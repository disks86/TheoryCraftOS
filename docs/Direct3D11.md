# Direct3D 11

`d3d11.dll` (src/Windows/d3d11) is Direct3D 11 as a layer on this system's Direct3D 12 - what Windows calls "11 on 12". `d3d12.dll` is the
user-mode half of the kernel's Direct3D driver ([Direct3DKernelMode.md](Direct3DKernelMode.md)); `d3d11.dll` uses its public interfaces and
one private call. The same source is built for 64-bit and for 32-bit programs ([Wow64.md](Wow64.md)).

## How it works

A device is a Direct3D 12 device, one command queue and one command list. The immediate context only remembers what is bound; a draw works
out the Direct3D 12 pipeline of that state, sets on the list what changed since the last draw, and records the draw. The list is sent (the
queue runs it before it returns) when something has to be seen: `Flush`, a `Map` that reads, a `Present`, a query's `End`, a texture the list
drew into (or cleared, or copied into) that a draw samples, a texture the list sampled that becomes a target or is copied into. The kernel
keeps a texture bound the way a list first uses it, which is why those cases split the list (also a copy into or a clear of a texture the list
sampled, and a copy out of one it wrote).

**Writes to what a recorded draw reads** do not send the list. Sending it is a whole trip to the GPU and back, and Chrome (ANGLE, for Skia)
writes the buffer a recorded draw reads all the time: `Map` with `WRITE_DISCARD`, `UpdateSubresource`, buffer copies, and a different offset
into its streaming vertex buffer for every batch, which makes a new converted copy (see the input layouts below). Sending the list for each of
those took about 300 ms per composited frame. Instead the buffer gets other memory and the old is retired: kept, untouched, until the list
has run, then a spare for the next buffer of its size (`buf_rename`, `retire`, `take_upload` in d3d11.c). A converted copy has its own "used
by this list" mark (`converted_used`), apart from the buffer's, and a converted copy a recorded draw reads still sends the list when it is made
again. (Retiring it too made frames faster still, but on the 3D hardware Chrome's window then stopped updating now and then while typing into a
page: the GPU process went on drawing and presenting and the picture stayed. Not explained yet: the kernel took every submission, and the
virgl device is used one thread at a time (RenderNode's LockedDevice), so it is not a race on its object handles.) Texture uploads
(`UpdateSubresource`, `Unmap` of a dynamic texture) are recorded in order with the draws too. What waits for a list is capped
(`RETIRED_MAX`, 32 MiB); beyond that the list is sent first. In Chrome a page that repaints everything every frame went from 8 to about 30
frames a second.

**Buffers stay unmapped.** `d3d12.dll` keeps the CPU's copy of an upload buffer and sends it at `ExecuteCommandLists`. It compares every
*mapped* buffer with what it sent by a hash, byte by byte, at every submission, and sends one unmapped since then without comparing. So a
buffer here is mapped in Direct3D 12 only between the program's `Map` and `Unmap`; `Buf.data` stays valid all the time (d3d12.dll's `Map`
hands out the same memory every time), and a write the runtime does itself is marked with a `Map`/`Unmap` pair (`buf_touched`). The
constant ring is marked the same way when a list used it.

| Direct3D 11 | here |
|---|---|
| buffers | a Direct3D 12 buffer in an upload heap: `Map` hands its memory out, a draw uses its GPU address. A write while a recorded draw reads it gives the buffer other memory (see above). A buffer the GPU writes (`D3D11_BIND_UNORDERED_ACCESS`, `D3D11_BIND_STREAM_OUTPUT`) is in the GPU's memory (a default-heap buffer): `UpdateSubresource` and copies into it are copies the list makes, and what reads it on the CPU (a copy into a staging buffer, a vertex layout that converts it) sends the list and reads it back. `CreateBuffer` checks the rules of feature level 11_0 (usages, bind and misc flags, structured strides, raw views). |
| constant buffers | Direct3D 12 here has one block of constants for all stages. The block of a draw is put together from the buffers bound to the vertex shader's slots, in slot order, then the pixel shader's, the geometry shader's, the hull shader's and the domain shader's (a dispatch: the compute shader's), each as large as the shader declares it, and goes into a ring of upload memory - so a constant buffer may change between draws without the list being sent. Buffers are up to 64 KiB; `*SetConstantBuffers1` binds a window of one (first constant, number of constants). All the constants of a draw are at most 4096 bytes (the kernel's block). |
| textures | a Direct3D 12 texture in a default heap. The CPU reaches it through copies: `UpdateSubresource`, and `Map` of a dynamic or staging texture (a copy in memory, sent at `Unmap` or fetched at `Map`). Formats the kernel has no image of are kept in a wider one and converted texel by texel ([formats](#formats)). 1D textures (`CreateTexture1D`) are 2D textures a texel high: the kernel's shader translator takes `texture1d` / `texture1darray` as that. |
| arrays, cubes and volumes | `CreateTexture2D` with `ArraySize` > 1 (up to 256) is the kernel's `Texture2DArray`; with `D3D11_RESOURCE_MISC_TEXTURECUBE` and six layers its `TextureCube` (sampled by direction; `d3d12.dll` is told with `TcosD3D12ResourceOptions` that the next resource is a cube, as Direct3D 12 knows a cube only by its views); `CreateTexture3D` (`ID3D11Texture3D`, depth up to 256) its `Texture3D`. Their subresources are the program's (`MipLevels` as asked for, each slice of a volume's level through `UpdateSubresource`'s box or `Map`'s depth pitch), and the kernel keeps every level of them (a volume's levels half as deep each), on an adapter with levels of every image (the kernel's `kFeature2MipmappedLayers`: the CPU renderer and virgl; `d3d11.dll` asks Direct3D 12 below once, `dev_all_levels`, and on another adapter keeps one level of them as before). Arrays of cubes (`TEXTURECUBE` with `ArraySize` a multiple of six: the kernel's `TextureCubeArray`, `TcosD3D12ResourceOptions` of more than six layers) are sampled with `TextureCubeArray` shaders (SM 4.1). A shader resource view made without a description is a `TEXTURE2DARRAY`, `TEXTURECUBE`, `TEXTURECUBEARRAY` or `TEXTURE3D` view; a view's `MostDetailedMip` / `MipLevels`, `FirstArraySlice` / `ArraySize`, `First2DArrayFace` / `NumCubes` are what the shader sees (`srv_desc12`: Direct3D 12's view of the same; a slice of an array as a `TEXTURE2D`, a cube of a cube array as a `TEXTURECUBE`, `E_INVALIDARG` for levels or layers the texture does not have or a dimension it cannot be seen as). |
| block-compressed textures | BC1, BC2 and BC3 (with their sRGB and typeless forms) are kept as they are: the rows of `UpdateSubresource`, `Map` and the initial data are rows of 4 x 4 blocks, and a box is on whole blocks. The kernel samples them as they are on the 3D hardware and decodes them for the CPU renderer ([Direct3DKernelMode.md](Direct3DKernelMode.md), *Block-compressed textures*). Sampled only; they are not copied with `CopyResource` / `CopySubresourceRegion`. |
| geometry, hull and domain shaders | go into the pipeline as they are (`gs_4_0` / `gs_5_0`, `hs_5_0`, `ds_5_0`: the kernel's, [Direct3DKernelMode.md](Direct3DKernelMode.md)); a draw with a hull shader needs a domain shader and a patch-list topology (`D3D11_PRIMITIVE_TOPOLOGY_n_CONTROL_POINT_PATCHLIST`). The pixel shader's (and the other graphics stages') views share the slots with the render targets. `ClearUnorderedAccessViewUint` / `Float` fill a buffer's range or a texture's level and layers with the values in the view's format. Of textures: a level and layers of a 1D, 2D (array) or 3D texture, also of a planar texture's planes (`R8_UINT` / `R8G8_UINT` and the 16-bit and `UNORM` forms) - the kernel's storage images ([Direct3DKernelMode.md](Direct3DKernelMode.md), *Storage images*), for compute shaders (`CSSetUnorderedAccessViews`) and pixel shaders (`OMSetRenderTargetsAndUnorderedAccessViews`); typed loads and stores of the formats kept as they are, atomics on R32_UINT / R32_SINT (`CheckFeatureSupport` `FORMAT_SUPPORT2` says which). Not of cubes, nor of levels the kernel does not keep. |
| buffers as shader resources | structured, raw (`BUFFEREX` with the raw flag) and typed views (`Buffer<>`: of a format the kernel has typed views of, else `E_INVALIDARG`); in the shaders' table beside the textures, up to t127. |
| depth textures | a texture made `R16_TYPELESS`, `R24G8_TYPELESS`, `R32_TYPELESS` or `R32G8X24_TYPELESS` with `D3D11_BIND_DEPTH_STENCIL \| D3D11_BIND_SHADER_RESOURCE` (a 2D texture, an array or a cube; one level, one sample) is a Direct3D 12 depth buffer that shaders read (a depth texture without `BIND_SHADER_RESOURCE` is made `DENY_SHADER_RESOURCE`). | texture and sampler pairs | a shader may read one texture with several samplers (each pair is a texture unit of its own below: [Direct3DKernelMode.md](Direct3DKernelMode.md)), and t<n> with any s<m>. |
| hazards | as in Direct3D 11, a resource bound for writing (a render target, a depth buffer, an unordered access view, a stream output target) is taken out of the shader resource (and vertex and index) slots, and a shader resource view of what is bound for writing is left empty. |
| render targets of levels and layers | on an adapter with levels of every image, render targets and depth buffers of any levels and layers are drawn into directly: a render target or depth stencil view's `MipSlice` is Direct3D 12's (the kernel's passes of a level, `kPassLevels`), with its layers of that level (a volume's `FirstWSlice` / `WSize` at the level; a view of several layers takes the geometry shader's `SV_RenderTargetArrayIndex`), and a level of a texture may be drawn into while a view of other levels of it is sampled. **The pixel shader's constants.** A Direct3D 11 pixel shader has constant buffers of its own, b0 .. b13, beside the vertex shader's. The
kernel compiles a shader's constant buffers end to end into the one block; for a pipeline made by `d3d11.dll` the pixel shader's begin where
the vertex shader's end. `d3d11.dll` reads the sizes out of the shaders (`dcl_constantbuffer`) and tells `d3d12.dll` the place with
`TcosD3D12PipelineOptions` (src/Windows/tcosdx.h) before it makes the pipeline; the kernel takes it with the shader
(`ShaderDesc::constant_base`, the escape `CreateShader`). All the constants of a draw are at most 4096 bytes.

**Depth clears.** Direct3D 12 here clears a depth buffer when the next pass with it begins, and forgets the clear with the list. A
`ClearDepthStencilView` is kept until a draw has followed it, and recorded again in every list until then.

## Formats

`formats.inc` says how each texture format is kept. Every colour format of feature level 11_1 is kept as it is: Direct3D 12 below has each with its own channels and
encoding (R8 / R8G8 / R16 / R16G16 in every kind, A8, R8G8B8A8 snorm and sint, R32G32 and R32G32B32, R11G11B10_FLOAT, R9G9B9E5, R10G10B10A2_UINT, B5G6R5, B5G5R5A1,
B4G4R4A4, BC1 - BC7 with their sRGB forms; docs/Direct3DKernelMode.md "More texture formats"), so the CPU's bytes are the GPU's. D16 is kept in 32-bit float,
D32_FLOAT_S8X24_UINT in D24S8 (with its stencil, 24 bits of depth). R24G8_TYPELESS and R32G8X24_TYPELESS not made for depth keep their bytes. `CheckFormatSupport`
answers from the table, and for the formats whose textures depend on the adapter (`FMT_EXTRA`: the ones the kernel numbers from 64) from Direct3D 12's format support,
which is what the adapter's device does with each (on virgl, the host's sampler and render masks). Textures are up to 16384 a side where the adapter has them (the CPU
renderer does; virgl as large as the host's `max_texture_2d_size`).

## What is not there

- Below `d3d11.dll`, in the kernel: depth buffers of several samples, or levels past the first, read by shaders, a depth texture read while it is the bound (read-only) depth
  buffer, a view of part of a depth array, a stencil view of a cube; `R1_UNORM` (not a format here: `CheckFormatSupport` answers none); on virgl
  `SV_RenderTargetArrayIndex` and `SV_ViewportArrayIndex` from a vertex or domain shader (`D3D11_FEATURE_D3D11_OPTIONS3` says FALSE there; the CPU renderer has them) and anisotropic
  filtering (virglrenderer 1.3.0 drops it: trilinear); on the GPUs other than virgl and the CPU renderer the blend factor and the fixed state of Direct3D 10 / 11
  ([Direct3DKernelMode.md](Direct3DKernelMode.md), "The fixed state of Direct3D 10 and 11"); `AntialiasedLineEnable` and the multisampled line modes (lines are aliased and
  one pixel wide); separate minification and magnification filters (a linear one of the two makes both linear).
- A vertex and a pixel shader that read one texture unit as different texture and sampler pairs (each stage numbers the units of its own extra pairs) do not go together in a
  pipeline (`E_INVALIDARG` at the draw's pipeline); SampleCmp of a mipmapped colour texture compares the base level on the GPU.
- A pipeline without a pixel shader runs d3d12.dll's pass-through one, whose runs `PSInvocations` counts (Windows says 0).
- Shared resources: textures made `D3D11_RESOURCE_MISC_SHARED_NTHANDLE` (with `SHARED` or `SHARED_KEYEDMUTEX`) are shared through NT handles
  (`IDXGIResource1::CreateSharedHandle`, `ID3D11Device1::OpenSharedResource1` / `OpenSharedResourceByName`, over d3d12.dll's shared resources). A texture made
  `SHARED_KEYEDMUTEX` has an `IDXGIKeyedMutex` (win32k's keyed mutex, shared with the texture's NT handle): `AcquireSync` (WAIT_TIMEOUT, WAIT_ABANDONED,
  DXGI_ERROR_INVALID_CALL when held already), `ReleaseSync` (sends what the device recorded first). Textures made `SHARED` or `SHARED_KEYEDMUTEX` without `NTHANDLE`
  have legacy handles: `IDXGIResource::GetSharedHandle` answers the global share handle (one number for every process; DXGI_ERROR_INVALID_CALL for a texture that has
  none), `ID3D11Device::OpenSharedResource` opens it (legacy handles only: `OpenSharedResource1` takes NT handles), with the keyed mutex's own global handle carried
  in the share's description. The legacy share ends with its creator's texture (Windows keeps it while an opener has it). Fences share through NT handles
  (above: Direct3D 11.2 - 11.4); not across adapters.
- Unordered access views above u7 and in the vertex, geometry, hull and domain shaders (`ID3D11DeviceContext::OMSetRenderTargetsAndUnorderedAccessViews` for those stages,
  64 slots), and `ForcedSampleCount`, are feature level 11_1's: this device is 11_0 (the kernel has them: [Direct3DKernelMode.md](Direct3DKernelMode.md), "Buffers"). A draw with
  no target at all draws only when its pixel shader declares unordered access views.
- `CheckFormatSupport` of the formats kept wider (R16G16_FLOAT and the like) does not say `TYPED_UNORDERED_ACCESS_VIEW`, though typed views of buffers of them are made: the
  flag would say textures too.
- `CreateInputLayout` does not compare the layout with the vertex shader's input signature (an input the layout has not is not refused).
- From the interfaces after 11.1: tiled depth buffers and multisampled tiled textures (the kernel's depth and multisampled images have no system-memory backing the tiles could be
  gathered into: no tiled depth format, no `D3D11_CHECK_MULTISAMPLE_QUALITY_LEVELS_TILED_RESOURCE` level), tiled cubes (`MISC_TEXTURECUBE` with `MISC_TILED` is refused), tiled
  textures of narrow formats as unordered access views, the status of buffer and unordered access loads (`ld_raw_s`, `ld_structured_s`, `ld_uav_typed_s`: refused by the kernel),
  residency feedback and clamps on virgl (tier 1 there: TGSI has neither); conservative
  rasterization on virgl, and tiers 2 and 3 (inner coverage, `SV_InnerCoverage`) anywhere; hardware content protection is a state only (protected content needs
  trusted hardware). `ID3D11InfoQueue` and `ID3D11Debug` (debug devices answer `DXGI_ERROR_SDK_COMPONENT_MISSING`, as Windows does without the SDK layers; the layered
  device exports answer the same), and a Direct3D 10 driver interface (`OpenAdapter10*`).
- Planar textures: typeless views of the planes, unordered access to them (`UNORM` views made, not drawn with, as for every texture; `UINT` ones refused), a render
  target view of several slices draws into the first (no `SV_RenderTargetArrayIndex`).
- Video: encoding (Direct3D 11 has no encoder interface; `D3D11_BIND_VIDEO_ENCODER` is refused), palettized formats, constriction, inverse telecine of cadences other
  than 3:2, 2:2, 2:2:2:4 and 2:3:3:2, downsampling to RGB (decoder output views are of YUV formats), content protection (above).
  The decoder's output must be at least its size. A planar alpha only blends a stream: one without it is drawn opaque, whatever its pixels' alpha.

## What it needed below it

- The kernel: a place for a shader's constant buffers in the block (above); a pipeline has the texture units its shaders read, not the
  number a root signature's table could hold (the CPU renderer takes no units for a pixel shader that samples nothing).
- `d3d12.dll`: the resources the descriptors of a table are views of go into the command stream's list of allocations (a draw that sampled
  a texture the same list had not also copied into was refused); a sampler's LOD limits are brought within what the kernel takes (`FLT_MAX`,
  the usual "no limit", was refused).
- The kernel does not carry two sets of values in the halves of one register between the vertex and the pixel shader (two `float2`
  outputs the compiler packs together): [Direct3D9.md](Direct3D9.md) found it and gives each a register. Not fixed.
- `dxgi.dll` no longer exports `D3D11CreateDevice`, `D3D12CreateDevice` and `D3D12GetDebugInterface` as stubs: a library linked against both
  got dxgi's.

## Finding out why nothing is drawn

A command stream the kernel's validator refuses is dropped whole and the program is not told. A kernel built with
`-DTCOS_TRACE_SERVICE_FAILURES=ON` says it on the debug console: "direct3d stream refused: command 10 after 11 commands, status ...
(Adapter.cpp line 536)" - the command is an `Op` of src/Kernel/Dxgkrnl/CommandStream.hpp, the line the check that refused a draw or a
binding (`dxgk::set_stream_trace`).
