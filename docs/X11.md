# The X server

TheoryCraftOS has an X Window System server in the kernel (`src/X11`). Linux programs reach it the usual way, with `DISPLAY=:0`, and Windows
programs can reach the same server through Winsock's `AF_UNIX`. The desktop is its window manager: each top-level X window is a window of the
desktop, made by the same code that shows the Windows programs' windows. An X window and a Win32 window therefore get the same frame, title bar,
buttons, taskbar button and Alt+Tab place, and the user moves, sizes, minimizes, maximizes, activates and closes them the same way.

| Part | Where |
| --- | --- |
| The protocol: setup, requests, resources, events, errors | `src/X11/X11Server.hpp`, `X11Requests.cpp` |
| Windows, properties and the window manager (ICCCM / EWMH), the desktop's view | `src/X11/X11Windows.cpp` |
| Drawing: clip lists, GC raster ops, lines, arcs, polygons, images, text, copies | `src/X11/X11Drawing.cpp` |
| Input: pointer and keyboard events, implicit and active grabs, crossing events | `src/X11/X11Input.cpp` |
| Keysyms, cursor-font shapes, colour names, font name patterns | `src/X11/X11Tables.cpp`, `X11Protocol.hpp` |
| The wire format in either byte order | `src/X11/X11Wire.hpp` |
| AF_UNIX listeners and the server's kernel thread | `src/X11/X11SocketServer.{hpp,cpp}` |
| The desktop side (the same as for Win32 windows) | `src/Desktop/Win32Windows.{hpp,cpp}` over `desktop::IWindowsSession` |
| Start-up | `src/main.cpp` (after the Windows bridge) |

## How it fits together

`x11::Server` implements `desktop::IWindowsSession`, the interface the desktop already used for win32k's windows
(`src/Desktop/WindowsSession.hpp`). The desktop holds a second `Win32Windows` (`Desktop::set_x11_session`) over the X server. That instance
makes the frames, forwards the user's actions (moves, sizes, state changes, activation, close), and hands keys and the mouse to the X server through
the same input taps the Windows programs use. Nothing about the frames is specific to either kind of program.

- **One coordinate space.** The X screen is the desktop's window manager area, and its monitors and work areas come from `set_display`. A
  top-level's requested position is its frame's (NorthWest gravity, as under a reparenting window manager). Its inside goes below the title bar,
  and `ConfigureNotify` and `_NET_FRAME_EXTENTS` report where it actually is. `StaticGravity` and override-redirect windows keep their inside
  where they asked.
- **The window manager inside.** The title comes from `_NET_WM_NAME` (UTF-8) or `WM_NAME` (Latin-1). These are honoured:
  - `WM_DELETE_WINDOW` for the close button; without it the client is disconnected, as `XKillClient` would do.
  - `WM_TAKE_FOCUS`, `WM_HINTS` (input, initial state), `WM_NORMAL_HINTS` (position flags, minimum and maximum size; a fixed size means no resize).
  - `WM_TRANSIENT_FOR`, which makes an owned window with no taskbar button.
  - `_MOTIF_WM_HINTS` without decorations, which gives no frame.
  - `_NET_WM_WINDOW_TYPE` (menus, tooltips and the like are popups; utility and toolbar windows are tool windows), `_NET_WM_STATE`
    (maximized, fullscreen, above, hidden, skip-taskbar).
  - The root messages `_NET_ACTIVE_WINDOW`, `_NET_CLOSE_WINDOW`, `_NET_WM_MOVERESIZE` (a drag of the frame by the desktop),
    `_NET_MOVERESIZE_WINDOW`, `_NET_REQUEST_FRAME_EXTENTS` and `WM_CHANGE_STATE`, and GTK's `_GTK_SHOW_WINDOW_MENU` (listed in `_NET_SUPPORTED`,
    as GTK checks): the frame's window menu opens where the client said (`take_window_menu`; the root coordinates made the window's).

  The server keeps `WM_STATE`, `_NET_WM_STATE`, `_NET_CLIENT_LIST`, `_NET_ACTIVE_WINDOW`, `_NET_WORKAREA` and the `_NET_SUPPORTING_WM_CHECK`
  window up to date. No other window manager can run: selecting `SubstructureRedirect` on the root fails with `BadAccess`.
- **Pictures.** Each top-level has one 32-bit picture of its inside. Subwindows draw into the part of it they cover, clipped by their ancestors,
  by the siblings above them and, under ClipByChildren, by their own children. There is no backing store: what a window loses is painted with its
  background and the client gets `Expose`, as on any server without one. The desktop draws the picture into the frame straight from the server's
  memory (`draw_window`), so an X window costs one copy, like a Win32 window.
- **Visuals and formats.** TrueColor depth 24 (the root's) and depth 32 (ARGB). Pixmaps can be depth 1, 8, 24 or 32. Image byte order and
  bitmap bit order are LSBFirst, with 32-bit scanline units and padding.
- **Fonts.** One core font with 8x16 cells (`Font8x16`, Latin-1 and Latin Extended-A through `glyph_of`) opens under any name. `ListFonts`
  knows `fixed`, `8x16`, `cursor` and two XLFD names. The `cursor` font gives glyph cursors, which become the desktop's own pointer shapes.
  Pixmap cursors (`CreateCursor`) become ARGB pictures, and `_NET_WM_ICON` becomes the frame's icon.
- **Keyboard.** Keycode = USB HID usage + 8, with a US map of two keysyms per key. The modifier map is Shift, Lock, Control, Mod1 = Alt,
  Mod2 = Num Lock and Mod4 = Super.
- **Extensions.** Only `BIG-REQUESTS`, for requests up to 16 MiB.

## Reaching it

`x11::SocketServer` listens on the system's AF_UNIX sockets (`src/Process/UnixSockets.hpp`) under the two names libxcb tries for `DISPLAY=:0`:

- the abstract name `/tmp/.X11-unix/X0`, which is one namespace for Linux and Windows programs. A Windows program connects with `AF_UNIX`,
  `SOCK_STREAM` and a `sun_path` that starts with a NUL (see `tests/windows/x11wintest.c`);
- the path `/tmp/.X11-unix/X0` of the Linux programs' tree, which is `/Linux/tmp/.X11-unix/X0` on the system's file system
  (`filesystem::layout::kX11SocketFolder`). The server makes it at start.

Linux and Windows programs both get `DISPLAY=:0` in their default environment. Any authorization is accepted: the server can only be reached from
inside the machine.

Locking: one `kernel::Mutex` guards the server. The desktop calls in under its UI lock, so the order is UI lock, then server. The transport moves
bytes under the system lock and feeds the server with that lock released, so the two are never held together. Events caused by the desktop wake the
transport's thread through a flag set under the system lock.

## Not done

- **Extensions.** There is no RENDER, XKB, MIT-SHM, RANDR, XInputExtension 2, SHAPE, XFIXES, Composite, GLX or DRI3. Toolkits that require
  them (GTK 3/4, Qt 5/6) do not start. Programs that use the core protocol (Xlib, Motif and Xaw programs, xterm with core fonts) are the target.
- **Fonts.** There is one core font, and no font server or scalable fonts. `QueryTextExtents` assumes 8-pixel cells.
- **Drawing.** Dashed lines are drawn solid. Join styles are ignored, and wide arcs are polylines.
- **Input.**
  - Passive grabs (`GrabButton`, `GrabKey`) are accepted but never activate.
  - `AllowEvents` and the synchronous grab modes do nothing.
  - No `LeaveNotify` is sent when the pointer moves from an X window to a desktop window.
  - `ChangeKeyboardMapping` and `SetModifierMapping` are acknowledged but change nothing, and the map is US only.
- **Selections.** They work between X clients only. They are not bridged to the desktop's clipboard (the Windows programs' clipboard is).
- **Window manager.**
  - Minimizing does not unmap the window.
  - Top-level borders (`border_width`) are not drawn.
  - A position without `USPosition` or `PPosition` is honoured when it is not (0, 0).
  - There are no virtual desktops.
- **TCP.** `DISPLAY=localhost:0` is not offered. Windows X clients built for TCP only (most VcXsrv-era builds) cannot connect; they need
  `AF_UNIX`.
- **Real programs in the OS.** No dynamically linked Linux X program (libX11 in `/Linux`) has been run in QEMU yet. The real-library tests run on
  the development machine against the same server code, and the in-OS tests use the raw protocol.
