# COM between processes

A Windows program can use an object that lives in another process: it asks for a class with `CLSCTX_LOCAL_SERVER`, Windows starts the program
(or the service) that serves the class, and the caller gets a *proxy* whose methods run in the server. Installers and updaters are built this way
(Google's updater, which installs Chrome, does all its work in a service that it talks to through COM), and so are Office automation and many
shell extensions.

`ole32.dll` here does this with a design of its own (`src/Windows/ole32/remote.inc`). It is not DCOM's wire protocol and cannot talk to another
machine or to Windows' own COM; both ends are always this library. For programs that only use the COM API that makes no difference.

## How it works

- **Endpoint.** A process that hands objects out listens on a named pipe, `\\.\pipe\tcos-com-<process id>`. Each connection has a thread that
  reads a request, carries it out and writes the reply. A caller keeps its connections to a server open and uses a free one (or opens one more) for
  each call, so calls from several threads, and calls made inside a call, do not wait for each other.
- **Objects.** The standard marshaler writes the same `OBJREF` as before; the OXID in it now ends in the owner's process id. Unmarshaling in
  another process asks the owner to hand the marshaled reference over and makes a proxy for the object (one proxy per object, so its `IUnknown`
  is always the same pointer). The owner keeps count of what each client process holds, and lets go when the client releases its proxy or when
  the client's last connection closes because it ended.
- **Interfaces.** A proxy answers `QueryInterface` by asking the owner. `IClassFactory` is built in. Every other interface needs a **type
  library**: the registry's `Interface\{iid}\TypeLib`, which every `oleautomation` or dual interface has (Windows' own "universal marshaler",
  `PSOAInterface`, works from the same information). The type library says what each method takes, and the arguments are sent accordingly.
  A proxy's virtual table is 64 small pieces of code that pass their slot number and the caller's arguments on; the owner's side rebuilds the
  arguments and makes the call.
- **Activation.** A server announces each class it registers with `CoRegisterClassObject(..., CLSCTX_LOCAL_SERVER, ...)` under
  `HKLM\SOFTWARE\TheoryCraftOS\COM\Running` (the registry is in memory and shared by all programs). `CoGetClassObject` looks there. If nobody
  serves the class it starts what the registry names: the service of the class's AppID (`AppID\{...}\LocalService`, with its
  `ServiceParameters` as the service's arguments), else the class's `LocalServer32` command line; then it waits up to 30 seconds for the
  announcement.

## What is sent

Integers of every size, `BSTR`, text that ends in a zero (`[in, string] const WCHAR *`, which Chromium's interfaces use), interface pointers (which become proxies on the other side: a callback is a call the other way), `VARIANT`
holding any of those, and pointers to those for results (`[out]`, `[out, retval]`, `[in, out]`). A method's `HRESULT` comes back as it is.

Not sent, so a method that has one fails with `E_NOTIMPL`: structures, arrays (`SAFEARRAY`), floating point arguments of a 64-bit program
(they travel in registers this code does not read), and interfaces with more than 64 methods. `IDispatch`'s own four methods are not carried
either: a dual interface is called through its virtual table, not through `Invoke`.

## What is different from Windows

- **No security.** Any process may call any object another one handed out. `CoImpersonateClient` answers "the caller is in this process",
  `CoInitializeSecurity` and `CoSetProxyBlanket` succeed and do nothing.
- **Incoming calls arrive on the endpoint's threads**, whatever apartment made the object, as for a free-threaded object. A single-threaded
  apartment's objects are therefore called from another thread; there is no message pumping while a call waits.
- **No proxy/stub DLLs.** An interface whose marshaling is in a DLL generated by MIDL (not a type library) cannot be called across processes:
  `QueryInterface` on the proxy fails with `E_NOINTERFACE`. `rpcrt4.dll` is still a stub.
- A proxy passed on to a third process is an object of the middle process that forwards its calls.
- The services `RpcSs`, `RpcEptMapper` and `DcomLaunch`, which services that serve COM objects depend on, count as running: what they do on
  Windows is in this library.

## Tests

`tests/windows/com32.c` with the interfaces of `com32.idl` (their type library is made by `widl` and is a resource of the program) is one program
in three roles: the client, a local server and a service. The client registers everything, creates an object of each class - which starts the
other two - and checks calls with numbers, strings, 64-bit values, VARIANTs, objects returned by methods, a derived interface, callbacks, errors,
and four threads calling at once. `tests/wow64_qemu.sh com32` runs it as a 32-bit program in the real kernel.
