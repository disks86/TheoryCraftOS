# Dell XPS 15 2-in-1 9575 (Core i7-8705G / i5-8305G, Kaby Lake-G)

Two GPUs on one package: Intel HD Graphics 630 (Gen9.5, PCI `0x591B`) and a Radeon RX Vega M GL (a Polaris-family chip with HBM2, which amdgpu calls VEGAM; PCI `0x694E`, GH is `0x694C`).
The internal panel is wired to the Intel GPU, so the Intel GPU is the boot display and the Vega M is a discrete adapter that `GpuManager` puts to sleep.

| Piece | Intel HD 630 | Radeon RX Vega M |
| --- | --- | --- |
| Identified (`*_gpu_identify`) | yes | yes |
| Boot display / mode setting | `IntelGpu` native path (Gen9.5, unvalidated on hardware) | UEFI GOP only (no Polaris display driver) |
| Video decode | `VideoCodec/Intel` (AVC, HEVC, VP9, MPEG-2, VC-1 via the VCS ring, simulated tests only) | H.264, H.265, MPEG-2 and VC-1 on `AmdUvd6VideoEngine`, opt-in (`TCOS_AMD_UVD`), tested in simulation, **not run on hardware** (below); the other codecs on the CPU |
| 3D acceleration | `Gen9GraphicsDevice` on the render engine, opt-in (`TCOS_INTEL_RENDER`), tested in simulation, **not run on hardware** (below) | none (CPU renderer) |

- **Hardware 3D** on the Vega M: a GCN4 PM4 path. The shader side exists in `src/Hardware/GraphicsProcessingUnit/AMD/Gcn` (a GCN3 assembler checked against LLVM, a wave emulator, a TGSI parser and TGSI-to-GCN compiler, and `GcnDraw`, which runs compiled shaders on the emulator for a draw call); `GcnState` emits the draw as PM4 packets (shader programs and user data, SPI/CB/PA/VGT state, `DRAW_INDEX_AUTO` / `DRAW_INDEX_2`, cache flush and fence) with register numbers generated from the kernel headers (`scripts/gen_gcn_registers.py`), and `GcnCp` is a model of the command processor that executes such a stream on the emulator. `AmdVegaDraw` puts shaders, constants, descriptors, vertices and the colour buffer in the card's framebuffer area (SDMA upload), submits the stream with `submit_graphics` and copies the picture back; the test runs that whole path against the simulated card, with `GcnCp` standing in for the command processor. The back end is modelled as well: a colour target that is linear or 1D tiled (`GcnTiling`: the GB_TILE_MODE entry names the layout, 8 = ARRAY_LINEAR_ALIGNED, 9 = ARRAY_1D_TILED_THIN1 with display micro tiles), blending (`CB_BLEND0_CONTROL`, constant colour, write mask), a 32-bit float depth plane and an 8-bit stencil plane (`DB_*` registers: tests, three stencil operations, masks), and image / sampler descriptors in the descriptor table (`GcnTexture`: the T# and S# word layouts from the kernel headers, R8 / RGBA8 / RGBA32F 2D images, linear or tiled, wrap / mirror / clamp / border, point and bilinear). `AmdVegaDraw` takes these in the request and hands back the colour, depth and stencil planes in their layout. The 2D tiled layouts (ARRAY_2D_TILED_THIN1: macro tiles over the pipes and banks, tile splits, the VEGAM's 16-pipe P16_32x32_16x16 rotation) are implemented in `GcnTiling` from AMD's address library source (egbaddrlib / siaddrlib / ciaddrlib), so the golden table's depth entries (0 to 7) and colour entries 10 and 14 work for colour, depth, stencil and textures (padding to whole macro tiles, base alignment `surface_base_align`, `AmdVegaDraw::area_alignment`); the micro tile pixel orders were checked against `ComputePixelIndexWithinMicroTile`. `scripts/gen_tiling_vectors.cpp` produces reference sizes and addresses from the address library itself for `tests/data/gcn_tiling_vectors.txt`, which `GcnTextureTest` compares with when the file is there (not generated yet: the 2D arithmetic is checked only as a bijection and for the alignments the table implies). Two sided stencil (front or back by winding and `PA_SU_SC_MODE_CNTL.FACE`) and the depth bounds test (before the stencil test) are in. Not done: PRT, thick and 3D tiling modes, more than one slice or sample, mip levels / cube / array / 3D images, anisotropy, dual-source blending, logic ops, hierarchical Z; _base_align`; `AmdVegaDraw::area_alignment`); the micro tile pixel orders were checked against `ComputePixelIndexWithinMicroTile`. `scripts/gen_tiling_vectors.cpp` produces reference sizes and addresses from the address library itself for `tests/data/gcn_tiling_vectors.txt`, which `GcnTextureTest` compares with when present (it has not been generated yet: the 2D arithmetic is checked only for being a bijection and for the alignments the table implies).
